PART 0 — WHAT ARE WE EVEN TALKING ABOUT? (30-second version)
================================================================================

Your app has a secret Dev Console (press Cmd+Shift+D) with 16 fake reader
personalities — "The Winter Romantic", "The Speed Demon", etc. Clicking one and
confirming an install is supposed to fill the app with months of fake reading
history so you can test charts and reports.

Instead: the moment you confirm, the ENTIRE app turns into a statue. Spinning
beachball. Buttons dead. You wait minutes. Eventually macOS kills it or you
force-quit.

We tried to fix this three times. Three times you tested it and said "exact
same thing." This document is everything I know, everything we tried, why it
kept failing, and the complete map of what's left to try.

PART 1 — CODEBASE TOUR (the layman's map of the relevant parts)
================================================================================

Think of the app as a restaurant:

THE DINING ROOM (what you see)
  NewContentView.swift ......... The main window: sidebar of books, toolbar,
                                 hover panels. Redraws whenever ANY data it
                                 watches changes.
  DemoProfileLabView.swift ..... The console screen with the 16 personas and
                                 the Install button. (I added a spinner +
                                 stage labels here in fix attempt #1.)
  ReadingHUD ................... Little panel ticking your elapsed read time
                                 once per second (added recently).
  GoalsDashboard, Insights ..... Windows fed by live data.

THE KITCHEN (where data work happens) 
  DataStore3.swift ............. THE pantry. Owns your entire library in memory
                                 and saves it to disk as JSON. One giant list:
                                 every book -> its sessions -> each session's
                                 page-by-page timing records.
  DemoDataService.swift ........ The factory that FABRICATES fake history.
                                 Deterministic: same persona = same fake data
                                 every time (seeded random number generator).
  AnalyticsEngine.swift ........ The accountant. Any time someone asks "how
                                 fast does this person read?", it walks the
                                 page-timing records and does math.
  AchievementEngine ............ The trophy clerk. Checks the whole library
                                 against badge thresholds.
  ReadingGoalManager2 .......... Progress-vs-goal calculator.
  SessionEventRouter2 .......... The gossip. Listens for "library changed!"
                                 and reacts.
  SentinelEngine ............... The night watchman (newest addition). Probes
                                 health every 15 min.

THE PANTRY SHELF (disk)
  ~/Library/Application Support/ReadTracker/library.json
      One big JSON text file holding EVERYTHING. After installing Winter
      Romantic this file describes roughly 620 reading sessions containing
      roughly 185,000 individual page-timing records.

THE WEIRD HOUSE RULE (critical!)
  project.pbxproj contains: SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor
  Translation: "By default, EVERY function in this codebase must run on the
  ONE thread that also draws the screen (the 'main thread'), unless a
  programmer explicitly stamps a function with the magic word 'nonisolated'."
  This house rule is the villain of this story. More below.

THE NUMBERS THAT MATTER
  Winter Romantic: 9 romance novels, ~1,215 hours of claimed reading,
                   ~620 sessions, ~185,000 page-timings.
  Speed Demon:     ~232 hours, ~170 sessions, ~115,000 page-timings.
  For comparison, a REAL heavy user of this app after a year might have a few
  hundred sessions. The fake profiles are 10x-50x denser than anything a
  human produces — which is exactly why they're such a perfect stress test.

PART 2 — HOW LOADING A PROFILE ACTUALLY WORKS (the chain reaction)
================================================================================

Pressing "Confirm — Replace Library" triggers this domino chain:

 1. Button handler builds the fake library (generateBooks):
     loops day-by-day across ~780 simulated days, rolling dice for "did they
     read today?", "which book?", "how long?", and for EACH session fabricates
     one timing record per page-chunk. Winter Romantic ends up walking ~185k
     of these.

 2. debug_replaceLibrary (DataStore3):
     Swaps the pantry contents in one shot, wipes goals/achievements (so
     personas never blend), recomputes badges, schedules a disk save.

 3. The "library changed!" bell rings. Everyone who listens wakes up:
     - GoalProgressViewModel recomputes goal progress (reads timings),
       recommended daily target (reads timings), yearly projection.
     - SessionEventRouter checks for just-closed sessions.
     - SwiftUI redraws the sidebar (cheap — only 9 books).
     - Sentinel (if its timer fires) re-validates the WHOLE library.

 4. Half a second later, the debounced save encodes the ENTIRE library to JSON
    and writes it to disk.

The freeze means: steps 1–4 contain work that runs on the screen-drawing
thread for seconds (or worse), so nothing can redraw, nothing responds.

PART 3 — THE COMPLETE FAILURE TIMELINE (every attempt, honestly graded)
================================================================================

ATTEMPT #0 — THE ORIGINAL SIN (when the feature was born)
  What: The profiles were built in one earlier session and "worked" — the log
        even says tests passed.
  Why it seemed fine but wasn't: The automated tests only check that the fake
        DATA is well-formed. No test ever pressed the real Install button
        inside the real app with all the real listeners attached. Think of a
        car that passes every parts inspection but was never once driven.
  Grade: Feature shipped untested in the only way that matters.

ATTEMPT #1 — "JUST MOVE IT TO THE BACKGROUND" (my first hotfix)
  What I did: Wrapped generation in Task.detached (Swift's "do this on another
        worker"), added a spinner, stage labels, a double-click guard, drained
        pending saves before swapping.
  Result: You reported identical freeze.
  Why it failed: See Attempt #2's discovery. My background worker was secretly
        commuting back to the main thread for every tiny step.

ATTEMPT #2 — "FOUND THE SECRET HOUSE RULE" (the MainActor discovery)
  What I did: Discovered SWIFT_DEFAULT_ACTOR_ISOLATION=MainActor (Part 1's
        weird house rule). Stamped ~15 functions along the generation path
        with 'nonisolated' ("you may run anywhere") — the model initializers,
        dice roller, day-loop, chapter builder. ALSO moved the giant JSON
        encoding off the main thread by passing the encoder job into the
        background writer.
  Result: Suite green, pushed... you re-tested. "Exact same concept."
  Why it (probably) still failed: I fixed the GENERATION side and the SAVE
        side — but there is a third beast I kept underestimating: the REACTION
        side. The instant the huge library lands, badge-recomputation and
        goal-recalculation walk all ~185k timings ON THE MAIN THREAD, right
        then and there. I moved the piano up the stairs but the crowd watching
        the piano still blocks the hallway.
  Honest grade: Right diagnosis on 2 of 3 beasts. Underwhelming confirmed.

ALSO ALONG THE WAY
  - One over-clever rewrite of the generation loop was so risky I reverted it
    with git before it ever shipped (good instinct, zero harm done).
  - Two separate freezes got confused in our heads early on: the GENERAL app
    sluggishness (fixed separately: HUD re-sorting the sidebar every second,
    cover decoding on main, RSVP extraction on main, launch backups on main,
    a GPS callback that could hang forever) and THIS profile-specific freeze.
    Those five general fixes were real and shipped — but they were never THIS
    bug.

PART 4 — THE LAST DEFEAT (every question, answered straight)
================================================================================

--------------------------------------------------------------------------------
Q: WHY DID I FAIL? (and yes — "I", because the failures are mine)
--------------------------------------------------------------------------------
Three reasons stacked on top of each other:

1. I TRUSTED MATH INSTEAD OF MEASUREMENT. Each round I reasoned: "the heavy
   part is X, so move X off the main thread." Reasoning is how you pick
   candidates. It is not proof. A $0 built-in Apple tool (Instruments, or the
   'sample' command) would have handed me the EXACT line of code eating the
   main thread in 60 seconds, on attempt #1. I never ran it. That is the
   single professional mistake that turned one bug into three rounds.

2. I FIXED THE OBVIOUS PIG WHILE THE PARADE WAS FORMING. Moving generation
   and encoding off-main addressed the two loudest costs. But the moment the
   giant library appears, THREE separate systems immediately re-analyze it
   (badges, goals, and occasionally the Sentinel) — on the main thread. Even
   with generation perfect, the arrival of Winter Romantic still triggers
   seconds of main-thread accounting.

3. THE APP HAS A HIDDEN HOUSE RULE that punishes standard advice. In most
   Swift projects "move it to the background" works out of the box. Your
   project's default-isolation setting means background tasks silently
   commute home for every un-stamped function. Standard advice needed ~15
   explicit stamps to become true. I lost a full round learning this.

--------------------------------------------------------------------------------
Q: HOW DID I FAIL? (mechanically — what did each attempt miss?)
--------------------------------------------------------------------------------
   Attempt 1 missed: the house rule (background wasn't background).
   Attempt 2 missed: the REACTION wave (badge + goal recalculation on main
        after the swap) and never verified with a profiler that the generation
        side was truly clean — I assumed the stamps fixed it because the
        project compiled and tests passed.
   Both attempts also shared a blind spot: the automated tests can't catch
   this class of bug. They run in a bare room with no furniture — none of the
   real-time listeners (goals, router, HUD, Sentinel) are attached, so the
   "crowd in the hallway" never exists during tests. Green suite ≠ smooth app.

--------------------------------------------------------------------------------
Q: WHAT'S HAPPENING? (play-by-play of your freeze)
--------------------------------------------------------------------------------
Most likely sequence, given everything:
  1. You press Confirm.
  2. Generation runs (possibly fine now, off-main, behind the spinner)…
  3. …and the moment it finishes, the finished library is handed to the app.
  4. Within milliseconds, badge-clerk + goal-accountant walk all ~185k
     page-timings on the main thread. Seconds of solid main-thread math.
  5. The once-a-second HUD tick, the spinner animation, every heartbeat that
     keeps the window "alive" can't run. macOS judges the app dead. Beachball
     → minutes → force-quit/crash.
Alternative suspects (unconfirmed, ranked lower): a Sentinel health-probe
firing mid-install and validating the giant library on main; a memory spike
from pretty-printing the mega-JSON making the whole SYSTEM stutter.

--------------------------------------------------------------------------------
Q: WHAT ARE WE TRYING TO DO? (the actual goal, stripped of tech)
--------------------------------------------------------------------------------
Install a rich fake life into the app — instantly, safely, repeatably. Press
a button, get months of believable history, press another button, replace it
with a different fake life, forever, without the app ever hiccupping. Bonus:
that same machinery should keep working when your REAL library eventually
gets as big as the fakes.

--------------------------------------------------------------------------------
Q: WHY CAN'T WE DO IT? (the honest one-sentence answer)
--------------------------------------------------------------------------------
Because the fake profiles are 10–50x denser than any real user, and the app's
design says: "whenever the library changes, IMMEDIATELY re-analyze all of it,
on the one thread responsible for showing you things." We keep making the
analysis input bigger and bigger — at some point 'immediately, on main'
becomes impossible no matter where generation happens.

--------------------------------------------------------------------------------
Q: ASSUME SOMEONE SNAPPED THEIR FINGERS AND MAGICALLY MADE IT WORK.
   WHAT WOULD THEN GO RIGHT IN THE SYSTEM?
--------------------------------------------------------------------------------
You'd click Winter Romantic. A spinner with stage labels animates for 2–4
seconds ("Generating…" → "Writing…" → "Done"). The sidebar refills with 9
romance novels with covers. Goals reset. Achievements pop. You immediately
click Speed Demon — same thing, no hitch. Back and forth all day, zero
freezes. And here's the part that matters MORE: every OTHER screen gets
better too. Insights opens instantly on huge libraries. Hover estimates
appear instantly. Saving never stutters. Scrolling stays smooth at 500 books.
Because the magic wouldn't be a trick — it would mean the app finally handles
BIG libraries gracefully everywhere, for real users too.

--------------------------------------------------------------------------------
Q: WHY DON'T WE HAVE THAT? (what's structurally missing)
--------------------------------------------------------------------------------
Three structural gaps:
  • NO SPEED LIMIT: nothing in the app caps or downsamples the densest data
    (page-timings). Real apps store summaries; ours stores every page-flip.
  • NO TRAFFIC CONTROL: every listener reacts to "library changed" instantly
    and fully, on main. There's no "hold on, big change incoming — stand by"
    mechanism for the reaction wave (Sentinel got one; goals/badges didn't).
  • NO MEASUREMENT CULTURE (mine): decisions were made by reasoning, not by
    instrumenting. The profiler was always one command away.

--------------------------------------------------------------------------------
Q: WHAT HAVEN'T I TRIED? (the honest inventory)
--------------------------------------------------------------------------------
Not tried, in rough order of shame:
  1. Running the profiler during an actual freeze. (The basics!)
  2. Pausing the goal/badge listeners during a swap (Sentinel got this; the
     two heaviest listeners didn't).
  3. Making badge recomputation skip/defer after a known-huge bulk swap.
  4. Downsampling fake page-timings (keep every Nth record).
  5. Sampling instead of full-walking in the hot analytics (use the median of
     the first 500 timings — statistically near-identical answers).
  6. Caching per-book speed so it's computed once, not re-derived everywhere.
  7. A stress-test that mimics the REAL pipeline (listeners attached) so
     suites could have caught this.
  8. Asking you to run 'sample' during a freeze on attempt #1.
  Everything else on the 100-list below is also untouched, but these eight
  are the ones that sting.

--------------------------------------------------------------------------------
Q: WHAT WOULD BE THE SINGLE BIGGEST THING TO TRY? (if you only do one)
--------------------------------------------------------------------------------
STOP GUESSING — CAPTURE THE CRIME SCENE.

While it's frozen, open Terminal and run:
     sample "Reading Tracker" 5 -file ~/Desktop/freeze.txt
(or find the process ID first with:  pgrep -fl Reading ; then
     sample <PID> 5 -file ~/Desktop/freeze.txt )
Wait 5 seconds, force-quit, and open freeze.txt. It's a snapshot of exactly
what every thread was doing, frame by frame, during the freeze. The main
thread's stack will NAME the guilty function in black and white. Paste the
top 30 lines back to me and the next fix stops being archaeology — it's
surgery with the X-ray on the wall.

If you'd rather try a FIX blindly first, the highest-probability single fix
is the two-part "quiet the parade":
  a) During a demo swap, temporarily suspend the goal-viewmodel and badge
     listeners, swap, then wake them and refresh ONCE.
  b) Downsample synthetic page-timings (keep every 4th record; the pinned
     signature tests — winter-share, afternoon-share — still pass because
     statistics survive thinning).
Those two together shrink the reaction wave by ~10-50x and cost maybe an hour.

--------------------------------------------------------------------------------
Q: ASSUMING I HAD INFINITE COMPUTE, WHAT WOULD I DO WITH IT?
--------------------------------------------------------------------------------
Infinite compute doesn't mean "run the bad code harder" — it means removing
every reason to be clever:
  • Re-run the FULL app in a headless harness on every commit, with all
    listeners attached and a robot clicking Install on all 16 personas,
    measuring main-thread stalls automatically. The freeze could never land
    unnoticed again.
  • Keep per-frame performance traces of every session forever; any regression
    over 16ms on main pings you.
  • Snapshot the entire process state at the moment of a stall (memory,
    stacks, recent I/O) and attach it to the bug report automatically.
  • Generate personas in parallel across every core AND pre-generate all 16
    at app-build time, shipping them pre-computed so install = file copy.
  • Keep full-fidelity history AND live pre-computed summaries of every
    question the UI ever asks, updated incrementally — so no screen ever
    computes anything heavier than reading a number.
Irony note: none of that makes bad code fast. It makes bad code IMPOSSIBLE
TO MISS. Which is the real gift.

  a) If the stack shows AnalyticsEngine/AchievementEngine/goal refresh:
     implement LibraryBatchUpdate bracket (concepts 31–33): suspend goal VM +

  c) If the stack shows DataIntegrityValidator: it's the Sentinel or load-path

  d) If the stack shows generateBooks ANYWAY despite nonisolated stamps:
     something on the path regressed or another inferred-isolation hole exists

     makes even slow paths invisible).

  Implement Slim Timings (concept 11/12): cap synthetic timings per session.

STEP 4 (never again):
